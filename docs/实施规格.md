# 双向刮刮卡 · 第一版实施规格

状态：开发基线建议，2026-09-27。依据原始需求与架构草稿整理。下文补充的默认值可在开发过程中调整。

## 1. 产品范围

一个部署对应一位人类和一位 AI 助手。人类通过网页操作，AI 通过 MCP 操作。双方给对方写卡、奖励积分、记录留言，各自花自己的积分刮对方写的卡。

不做多人账户、排行榜、签到、过期积分、惩罚扣分、催促通知或奖品自动履约。卡片内容是双方约定的文字惊喜，展示后不自动执行命令或操作外部服务。

## 2. 身份与权限

身份固定为 `human` 和 `llm`，昵称仅影响展示，不参与权限判断。卡片归属者是刮卡方，作者是另一方。

| 操作 | 网页 / human | MCP / llm |
| --- | --- | --- |
| 写卡 | 写给 llm | 写给 human |
| 奖励积分 | 给 llm | 给 human |
| 刮卡 | 刮归属 human 的卡 | 刮归属 llm 的卡 |
| 看余额和流水 | 双方均可见 | 双方均可见 |
| 查看密封内容 | 仅自己写的卡，通过作者接口 | 仅自己写的卡，通过作者查询 |
| 看已揭晓内容 | 双方均可见 | 双方均可见 |
| 留言 | 署名 human | 署名 llm |
| 修改昵称 | 可以 | 不可以 |

服务器从认证入口确定身份；请求参数不能指定或覆盖操作者。网页与 MCP 使用不同 Token；MCP Token 不发送给浏览器。

## 3. 卡片生命周期

卡片状态：`draft → active → completed`，不能逆转。格子状态：`sealed → scratched`，不能逆转。

- 双方各有一个当前卡位，互相独立；不存在必须同步完成的“轮次”。
- 每个归属者最多一张 active 卡、一个 draft 草稿。已有 active 卡时可以准备下一张草稿，但不能发布。
- 草稿允许编辑、增减格子；不支持留言，不出现在对方列表里。第一版不单设删除草稿操作，可以覆盖修改草稿。
- 发布时统一校验所有格子，锁定价格、内容和格数，分配归属者自己的连续卡号，例如“小明的第 3 张”。内部 UUID 与展示卡号分开。
- 发布后不能修改、撤回或换卡；不设置有效期。若未来需要放弃卡片，应另行设计，不能偷偷删除账目。
- 最后一个格子刮开后自动 completed，记录完成时间并进入归档册。
- 首页没有 active 卡时保留最近完成卡的完成摘要，显示“这一张已经刮完，等下一份惊喜”；另一方卡位不受影响。
- 下一张草稿不自动发布，写卡方主动发布。

建议第一版每卡 1–12 格，价格为 1–1,000,000 的整数，内容 1–2,000 字；发布时所有格子必须完整。参数集中定义，之后可以调整。

## 4. 积分与账本

初始积分为 0。余额只由流水计算：奖励金额总和减去刮卡支出金额总和；用户或设置表不存 balance。

流水只有 `award` 和 `scratch` 两种类型，金额都为正整数。界面展示奖励 `+N`、刮卡 `−N`。“没有负数”解释为没有惩罚、没有负余额，并非隐藏正常支出。

- 奖励必须填写理由，允许 1–500 字；金额 1–1,000,000。
- 刮卡支出理由由服务器生成，关联卡片与格子，不允许客户端伪造金额。
- 积分不足直接失败，格子保持密封，不产生流水。
- 流水只追加，不能编辑或删除。第一版不提供任意调账入口。
- 余额使用整数计算；奖励需校验累计余额不超过安全整数范围。

所有会产生记录的写操作带 `request_id`：奖励、刮卡、创建/更新/发布卡片、写留言。相同身份、操作和 request_id 的重试返回原结果；相同键配不同参数返回冲突。客户端对同一次操作的重试复用原键；幂等不能识别使用了新键的语义重复奖励。

## 5. 密封和揭晓边界

密封是服务端的读取权限控制。刮卡方在揭晓前拿不到内容，不能把内容预先放进 HTML、DOM、Canvas、接口响应或前端资源，再靠遮罩隐藏。

读取分三种：

1. **卡片摘要**：卡号、作者、归属者、价格、格子状态、时间等，任何格子都不带内容。
2. **已揭晓结果**：只返回已 scratched 格子的内容，支持刷新、历史和归档查看。
3. **作者读取**：允许作者查看自己的草稿和已发布内容；与摘要接口分开，校验作者身份。

首次揭晓只发生在成功刮卡事务中。已揭晓结果可以随后读取，不再扣分。敏感响应设置 `Cache-Control: no-store`；不将内容或 Token 写入 localStorage、IndexedDB、Service Worker 缓存或日志。用户自己正在编写的内容和已揭晓结果当然会在其浏览器内存中出现。

SQLite 文件和备份对服务器管理者可读；第一版不承诺对部署者保密，也不宣称实现端到端加密。

留言是双方公开的文字。写卡者可自愿给提示，系统不自动把密封内容复制到留言。卡片内容、奖励理由和留言一律按纯文本渲染。

## 6. 刮卡事务与交互

服务端在 SQLite 写事务（如 `BEGIN IMMEDIATE`）内：

1. 检查幂等请求是否已完成。
2. 校验身份、卡片归属、卡片状态与格子状态。
3. 读取服务端价格，计算余额，检查足额。
4. 条件更新格子 `WHERE status = 'sealed'`，要求恰好更新一行。
5. 追加唯一的格子支出流水。
6. 如果所有格子已刮完，更新卡片完成时间与状态。
7. 保存幂等结果并提交；提交成功后才返回内容。

同一格不同请求重复刮，返回 `ALREADY_SCRATCHED`，不扣分；同一 request_id 重试返回原成功结果。不同格子同时刮也必须串行验证余额，避免透支。失败时全部回滚。

网页点选格子后先显示价格与当前余额，再点“花 N 分，开始刮”。确认后服务器完成扣分和揭晓，网页收到结果再启动刮层效果。界面明确提示“开始后扣分，关掉页面也能回来查看”。

刮动只是展示过程，不决定是否扣费。断网时提示“正在确认结果”，复用 request_id 查询/重试；不能提前显示“未扣分”。支持“直接揭晓”按钮和键盘操作，照顾不方便拖动的用户。

## 7. 碎碎念和归档

- 共用一本留言簿，每条留言必须关联已发布卡，可选关联该卡某个格子。
- 服务器验证格子属于该卡。一次成功刮卡与格子一一对应，第一版不额外建立刮卡事件表。
- 双方可在刮前、刮后及归档后多次留言。留言不可编辑、不可删除，发送前可预览。
- 筛选仅有卡片和留言者，不支持自定义标签。
- 按时间从旧到新阅读，以时间和 ID 稳定排序；首次打开定位最新页，筛选后显示匹配项 `n / N`，支持翻页和跳转。
- 建议一条留言一页，长内容在纸页内正常滚动；正文 1–2,000 字。手机使用单页。
- 归档册按卡片完成时间倒序；价格、内容、刮开时间和关联留言可查。卡片结果只读，但允许继续留言。

## 8. 数据模型

不单设 show_now 表：用卡片状态查询双方 active 卡，并通过数据库唯一约束保证每方最多一张。减少卡位与卡片状态不一致的机会。

| 表 | 主要字段和约束 |
| --- | --- |
| settings | 单个部署的两方昵称、初始化时间；环境变量提供默认昵称，网页填写后持久化值优先 |
| cards | id、owner、author、owner_sequence、status、created_at、published_at、completed_at；归属者与发布卡号唯一；每方 active / draft 各至多一张 |
| cells | id、card_id、position、price、content、status、scratched_at；卡内序号唯一 |
| ledger | id、beneficiary、kind、amount、reason、actor、source、cell_id、request_id、created_at；每格 scratch 流水唯一 |
| notes | id、card_id、cell_id 可空、author、body、created_at |
| requests | actor、operation、request_id、payload_hash、result_reference、created_at；三元组唯一，和业务写入同一事务 |

所有时间以 UTC 保存，前端按本地时区显示。开启外键约束；建立迁移机制。幂等结果优先记录实体引用，避免复制密封内容；重放结果仍经过身份校验。

## 9. MCP 工具契约

保持五个工具；列表查询有分页，不一次返回全部历史。

| 工具 | 参数方向 | 行为 |
| --- | --- | --- |
| scratchcard_status | section、card_id?、cursor?、limit?、note_author? | section 为 overview / history / ledger / notes / authored；默认 overview 返回余额和两张卡摘要，结果读取遵循可见范围 |
| scratchcard_award | points、reason、request_id | 给 human 加分 |
| scratchcard_create | cells、request_id、action、draft_id? | action 为 save_draft / publish；一次传入完整格子；可保存草稿或直接发布，指定 draft_id 可更新/发布已有草稿 |
| scratchcard_scratch | cell_id、request_id | llm 刮自己的格子，返回内容、花费、余额和是否完成 |
| scratchcard_note | card_id、cell_id?、body、request_id | 以 llm 身份追加留言 |

统一错误码至少包含：`UNAUTHORIZED`、`FORBIDDEN`、`VALIDATION_ERROR`、`INSUFFICIENT_POINTS`、`ALREADY_SCRATCHED`、`ACTIVE_CARD_EXISTS`、`IDEMPOTENCY_CONFLICT`、`NOT_FOUND`。

MCP 目标采用 HTTPS 下的 Streamable HTTP，使用 JSON 响应，不启用 SSE；具体 SDK 与客户端兼容性在接入阶段验证。网页接口和 MCP 入口共用业务服务，避免两套规则。

## 10. 技术与部署方向

建议 TypeScript、React、Node.js、SQLite，单仓库。先验证本地基础闭环，再实现完整交互。具体依赖版本在初始化时检查官方文档后锁定。

网页采用独立访问 Token 换取短期会话：Token 通过鉴权头发送，之后使用 HttpOnly / Secure / SameSite Cookie；写请求校验来源并防护 CSRF。Token 不进入 URL。MCP 使用独立 Bearer Token，两个入口不接受对方凭证。

外部访问全部 HTTPS，由 Nginx 提供 TLS；Node 仅绑定回环地址或 Unix socket，内部代理不暴露公网。进程由 systemd 管理。端口、数据库路径、默认昵称、两个访问 Token、公开访问地址全部可由环境变量配置。

仓库只放 `.env.example`，不提交真实 Token、服务器凭据、数据库或备份。部署前确认运行环境、域名解析和证书，不在需求整理阶段直接操作服务器。

SQLite 备份使用在线备份机制或停服一致性备份，不能在写入中随意复制单个文件。上线验收包括一次恢复演练。

## 11. 实施顺序与验收

### 阶段 A：数据和规则

初始化工程、数据库迁移、身份鉴权、卡片和积分服务。用集成测试验证越权、密封字段缺失、幂等冲突、并发同格、并发跨格余额不足、事务回滚、最后一格完成、双方独立换卡。

### 阶段 B：双向最小闭环

接入五个 MCP 工具和基础网页。人工完整走通双方各写一张卡、互相加分、各刮一格、刷新查看结果和流水。验证真实 MCP 客户端可在无 SSE 配置下连接。

### 阶段 C：完整体验

完成写卡预览、柔和刮动、手机适配、留言翻页筛选和归档。检查鼠标、触控、键盘、减少动画偏好及空白/失败状态。

### 阶段 D：部署交付

补充 README、MIT、配置示例、Nginx/systemd 模板、备份恢复说明。部署验收 HTTPS、重启持久化、Token 隔离、失败重试和数据恢复。

## 12. 接入阶段需要补充的信息

开始本地开发不依赖这些信息；到接入时再确定：实际使用的 AI/MCP 客户端、服务器系统和运行时、域名挂根路径还是独立子域名、现有 Nginx 站点情况。不得覆盖现有站点配置。
